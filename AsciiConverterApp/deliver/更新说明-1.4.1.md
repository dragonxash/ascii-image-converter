# 更新说明 — 1.4.1

**版本**：1.4.1（versionCode 9）
**上一版**：1.4.0（versionCode 8）
**主题**：修掉**「系统相册选的图读不出来（ENOENT）」** —— 根因是每次转换都拿原始 Uri 重新解码，
相册的临时授权经不起反复开。改成**选图时读一次、落到本地，之后只读本地文件**。

---

## 一、你报的现象，和它背后的真话

你的观察非常准，而且那句「用文件浏览器打开图片是没有问题的，但是用系统相册就这样」
已经把答案写在脸上了：

> **同一个 App、同一张图，两条路一个能读一个不能读 —— 那问题不在"读"，在"读了几次"。**

两个入口给的授权**根本不是一回事**：

| 入口 | 授权性质 | Uri 形状 | 反复开流 |
| --- | --- | --- | --- |
| **系统相册**（照片选择器） | **临时**，绑在这次选图结果上 | `content://media/picker/0/com.android.providers.media.photopicker/media/1001204890` | ❌ **开几次就开始 ENOENT** |
| **文件选择器**（SAF） | **可持久化**（本 App 主动申请的） | `content://com.android.externalstorage.documents/...` | ✅ 爱开几次开几次 |

文件名都是「打不开数据流」，但它**不是"文件不存在"**——是 provider 拒绝给你数据。
报错信息里那句 `open failed: ENOENT` 是 Android 最容易带偏人的一句话。

---

## 二、真正的原因：每转一次，就去开一次相册的 Uri

看这段（1.4.0 的实际代码）：

```kotlin
// ❌ 1.4.0 的写法
private fun loadImage(uri: Uri, name: String?) {
    sourceUri = uri            // ← 把相册的 Uri 存起来
    scheduleConvert(0L)
}

private suspend fun doConvert() {
    val uri = sourceUri ?: return
    val bitmap = PictureDecoder.decode(applicationContext, uri)   // ← 每次转换都重新开一次！
    ...
}
```

`doConvert()` 不是"转换一次"就完了——**它是"每次参数变一下就转一次"**：

- 拖一下「字符宽度」滑杆 → 转一次（滑杆是连续事件，一次拖动可能十几次）
- 切一个预设 → 转一次
- 点开「PC-98 画风」→ 转一次
- 调一下「原图彩色填充」→ 转一次

于是「选了一张图」这件事，实际等于**把相册那个 Uri 开成了十几次到几十次**。

文件选择器（SAF）给的是可持久化授权，开几十次毫无问题；
相册给的是临时授权，开到某一次就开始拒绝 —— 这就是你看到的现象。

> 顺带一提，报错里的**场景名是「转换图片」而不是「选图」**，这一点也很容易带偏排查方向：
> 看起来像是解码/转换逻辑出了问题，其实是"选完图之后的第 N 次重读"被拒了。

### 而且预览界面还有个加成效应

同一张图在批量页里的缩略图也是这样——列表滚动会**反复重新绑定**每一行，
原来每绑定一次就开一次 Uri。滚动两下，相册 provider 就该烦了。

## 三、修法：分成两层，用类型把错误写法堵死

### 第一层：`SourceCache`（新文件）—— 选图那一刻读一次，落本地

```kotlin
object SourceCache {
    /** 选完图立刻调用，之后这个 Uri 再也不碰。 */
    @WorkerThread fun materialize(context: Context, uri: Uri): File

    /** 只留最近两张。留一张做缓冲，避免"上一张正在解码、这一张选图顺手把它删了"。 */
    fun keepOnly(context: Context, keep: File?)

    /** 冷启动按年龄清理残留（崩溃/被系统杀掉留下的）。 */
    fun sweepStale(context: Context)

    /** 界面重建时把图接回来：只认文件、不认 Uri。 */
    fun existing(path: String?): File?
}
```

主界面里的调用点**只有一处** —— 选图回调：

```kotlin
private fun loadImage(uri: Uri, name: String?) {
    loadJob?.cancel(); convertJob?.cancel()
    loadJob = lifecycleScope.launch {
        val local = try {
            withContext(Dispatchers.IO) { SourceCache.materialize(applicationContext, uri) }
        } catch (e: CancellationException) { throw e }      // 取消不是失败，别弹框
        catch (e: Throwable) { reportSourceError(e, uri); return@launch }
        if (!isActive) return@launch                        // 又选了新图，这份丢弃
        SourceCache.keepOnly(applicationContext, local)
        sourceFile = local                                  // ★ 之后只认这个 File
        scheduleConvert(0L)
    }
}

private suspend fun doConvert() {
    val file = sourceFile ?: return
    val bitmap = PictureDecoder.decode(file)                // ✅ 只读本地文件
    ...
}
```

### 第二层：`PictureDecoder` 的签名里**干脆不接受 Uri**

```kotlin
object PictureDecoder {
    // ✅ 全类只有这一个 decode 重载，想传 Uri 都传不进来
    @WorkerThread fun decode(file: File, maxSize: Int = 2400): Bitmap
}
```

这一步是这次修复里**最关键的设计动作**。

只把调用点改成读本地文件，下次谁（包括三个月后的我自己）再加一个功能，
顺手还是会写 `decode(context, uri)`。把 Uri 参数从类型上删掉之后，
"再回去读一次 provider"这件事**编译期就做不到了**。

> 落盘放在 `cacheDir` 下：系统空间紧张时自己会清，不占用户的「应用数据」。
> 并发/时序上也做了保护 —— 只留最近两张、冷启动按 24 小时年龄清理残留、
> 界面重建（切语言、旋转）走的是文件路径而不是会过期的 Uri。

## 四、顺手加的三层加固（针对"读不到"本身）

就算只读这一次，也还是可能失败。所以读取层 `ContentStreams` 一并加强了：

### 1. 失败会**等一会儿整体重试**

```
第 1 轮失败 → 等 0.4s → 第 2 轮失败 → 等 1.2s → 第 3 轮失败 → 等 2.4s → 第 4 轮
```

**为什么要等**：图在云相册、本机没副本时，**第一次打开实际上只是"触发下载"**，
下载完再开就成了。1.4.0 是立刻失败的，等于把这种情况全判了死刑。

**为什么敢等**：因为同时判了"值不值得等"——

```kotlin
fun fail(name: String, cause: Throwable) {
    failures.putIfAbsent(name, "${cause.javaClass.simpleName}: ${cause.message}")
    if (cause !is SecurityException) permissionOnly = false   // 权限问题不用等
}
fun worthRetrying(): Boolean = !permissionOnly
```

权限被拒的话，等 4 秒还是被拒，所以直接放弃，不会让用户白等。

### 2. 照片选择器有专门的兜底路

照片选择器给的 Uri，**末段那串数字就是 MediaStore 的 `_id`**：

```
content://media/picker/0/com.android.providers.media.photopicker/media/1001204890
                                                                  ↑ 这就是 _id
```

所以现在会额外试这两条：

```kotlin
ContentUris.withAppendedId(MediaStore.Images.Media.EXTERNAL_CONTENT_URI, id)
ContentUris.withAppendedId(MediaStore.Files.getContentUri("external"), id)
```

某些机型上 picker 那一层转不出数据，但直接拿 id 问 MediaStore 能拿到。
没有媒体读权限时这两条会抛 `SecurityException`（被记一笔跳过，不影响别的路）。

打开方式从 4 种增加到 **7 种**（多加了 typed 访问、MediaStore 兜底、`_data` 真实路径）。

### 3. 失败时**自己把证据打出来**

原来失败只告诉你"三种方式都试过了"。现在会**再查一次 provider 的元信息**：

```
来源探测：
  可见列（18）：_id, _data, _size, _display_name, mime_type, is_pending, is_trashed, ...
  _data = null
  _size = 2415724
  is_pending = 0
```

判读表：

| 看到什么 | 结论 |
| --- | --- |
| `_data` 为 null / `is_pending=1` | 图还在云端，本机没副本（先在相册里打开一次下载下来） |
| 出现 `is_downloaded` 之类厂家私有列且为 0 | 同上，国产 ROM 的云相册很常见 |
| 连 `query` 都抛异常 | provider 连元信息都不给 → 授权八成已失效 |
| `query` 给得出 `_size` 但开不出流 | provider 的 open 实现有问题 → 换文件浏览器那条路 |

**下次再出问题，请把完整报错发我 —— 现在这份报错能直接把原因指出来了。**

## 五、还有三个一直在的小坑，一起修了

| 问题 | 原来的写法 | 现在 |
| --- | --- | --- |
| **fd 泄漏** | `FileInputStream(pfd.fileDescriptor)`，`ParcelFileDescriptor` 从头到尾没人关 | `ParcelFileDescriptor.AutoCloseInputStream(pfd)`，关流 = 关 fd |
| **交出去的流被提前关掉** | `strategy.open().use { ... }` —— 想让调用方拿到还开着的流，结果 `use{}` 在返回前关了它 | 加 `closeStream` 标志，交出去的走另一条分支 |
| **缩略图降采样提前一轮停手** | `while (max(w,h) / (sampleSize*2) >= maxPx)` —— 结果比目标大一倍，白占一倍内存 | `while (max(w,h) / sampleSize > maxPx)` |

还有个一直在的**稳定性隐患**：拖滑杆时会连续取消上一个转换任务，
而 `catch (e: Throwable)` 会连 `CancellationException` 一起吃进去、弹一个错误框。
现在 `CancellationException` 原样抛出，不当失败处理。

## 六、出错提示换了：多给你一条能走通的路

读图失败时不再只是"复制详情"，多了一个 **「换文件浏览器重选」** 按钮：
文件选择器走的是文档通道、拿的是可持久化授权，同一张图基本都读得动。
与其让你对着错误框发呆，不如把能走通的那条路直接摆在按钮上。

## 八、怎么验证

```bash
# 本轮新增：源图读取链路（41 项，含"谁还能碰 Uri、谁只能碰 File"）
python verify_source_pipeline.py

# 回归：确认没碰坏别的
python verify_string_formats.py
python verify_pc98_dither.py
python verify_pc98_palette.py
python verify_ansi_roundtrip.py
```

`verify_source_pipeline.py` 检查的是**结构特征**（这类规矩靠注释提醒是没用的）：

- `PictureDecoder` 里不存在吃 `Uri` 的 `decode` 重载，也不出现 `openInputStream`
- `doConvert()` 里出现的是 `PictureDecoder.decode(file)`，不出现 `contentResolver`
- `SourceCache.materialize` 在 `MainActivity` / `BatchActivity` 里**各只有一处**调用
- `ContentStreams.copyTo` 只被 `SourceCache` 一个人调用
- `ThumbnailLoader.load` 只收 `File`，且自己不碰 `ContentResolver`
- 重试 / MediaStore 兜底 / probe 三段加固都还在
- 新增的中英字符串都在，且两边条目数一致（151 = 151）

> 写这个脚本踩了一个小坑顺带记下来：注释里写「不要写成 `X`」，
> 会把 `X` 的检查判成失败 —— 说明写清楚反而过不了校验。
> 解决办法是比对前先把整行注释剔掉（但**不能**剔行尾注释，
> `content://` 里的 `//` 会被误伤）。这条也写进脚本注释了。

### ⚠️ 需要你实机确认的事

**这次的改动做了编译验证、包内核对和 41 项源码结构校验，但同样没有真机跑过**（开发机无设备）。

需要说清楚的一点：**「原来只开了一次」这个前提，我没能在这台机器上复现验证。**
你的那台一加 13（ColorOS / Android 15）才有条件验证。所以：

1. **请先用系统相册选一张照片试。** 如果还报错，把完整报错发我 ——
   这次报错里多了「来源探测」那一段，能直接看出是云端没下载、还是权限被拒、还是 provider 有问题。
2. **顺手试试这两种图，能区分情况**：
   - 一张**刚拍的照片**（肯定在本机）
   - 一张**很早以前的老照片**（很可能只在云相册）
   如果前者能读、后者报错且 `_data = null`，那就是云端问题，
   解法是先在相册里把它下载到本机（或者用「文件浏览器重选」）。
3. **滑杆多拖几下。** 这是原 bug 最容易被触发的动作（每拖一次都会重转）。
   现在重转读的是本地文件，理论上拖多少下都不会再碰相册。
4. **批量页也试试**（一次选十几张、然后上下滚动列表）。
   那条路原来比单图页更容易翻车，现在缩略图和转换共用同一份本地副本。
