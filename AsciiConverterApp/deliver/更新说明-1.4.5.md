## 一、为什么"什么都没发生"

**这不是一个 bug，是三个叠在一起**，而且**每一个都是静默的**——所以界面才会安安静静地停在「还没有图片」。
下面按"发生的先后"排。

### 原因 1（根因）：相机拿不到我们那个 Uri 的**写权限**

原来的写法用的是 androidx 的 `ActivityResultContracts.TakePicture()`。反汇编
`androidx.activity 1.11.0` 里的 `ActivityResultContracts$TakePicture.class`，
它的 `createIntent` 只做了两件事：

```
new Intent("android.media.action.IMAGE_CAPTURE")
    .putExtra("output", uri)          ← 就这些
```

**一次 `addFlags` 都没有。**

而"让相机能写我们的 `content://…fileprovider/…`"这件事，靠的就是 grant flag。
Manifest 里 `grantUriPermissions="true"` 的意思是"**允许**你把权限授出去"，
不是"已经授出去了"——这两者差得很远。

结果：相机（或那个选图界面）**没有写权限**，它往我们指定的文件里写不进去，
回来时那个文件还是 **0 字节**。

### 原因 2：`pendingCaptureFile` 没进 `savedInstanceState`

拍照要跳到另一个 App，而相机是**重型 Activity**。我们的界面在后台被系统回收重建是很常见的，
切个屏幕方向也算。重建之后：

```
pendingCaptureFile = null      ← 新实例，字段没了
```

于是拍照结果回到手上时，**文件对象找不到了**，即使相机老老实实写了照片也接不上。

### 原因 3：有结果、没文件时，旧代码直接**什么都不做**

```kotlin
// 旧代码
if (success && file != null && file.length() > 0) {
    loadImage(...)
}
// ← 不满足条件就静默返回，没有 else，没有任何提示
```

这一条把前面两条的后果**全部吞掉**，所以你看到的就是"点了、选了、回来了、啥也没有"。

## 二、改法

### 1. 换掉契约，改自己发 intent

用 `StartActivityForResult` 自己拼 `ACTION_IMAGE_CAPTURE`，这样能：
在 intent 上带 grant flag、**拿得到回传的 Intent**（`TakePicture` 只回一个 Boolean，别的全丢）。

### 2. 显式按包名授权

```kotlin
private fun grantCaptureUri(uri: Uri) {
    val probe = Intent(MediaStore.ACTION_IMAGE_CAPTURE)
    packageManager.queryIntentActivities(probe, PackageManager.MATCH_DEFAULT_ONLY)
        .forEach { info ->
            grantUriPermission(info.activityInfo.packageName, uri, CAPTURE_GRANT_FLAGS)
        }
}
```

为什么要按包名授、而不只是靠 intent 上的 flag：**有些 ROM 的相机是"转发"的**
（自己再起一个 Activity 去拍），转发时 flag 会丢。`grantUriPermission` 不经过 intent，
转发也还在。

授权范围只覆盖**刚创建的那一个拍照文件**，不会放宽别的目录。

### 3. 三条回退路，而不是只认一条

| 顺序 | 情况 | 处理 |
| --- | --- | --- |
| 1 | 相机按 `EXTRA_OUTPUT` 正常写进了我们给的文件 | 直接用 |
| 2 | 不认 `EXTRA_OUTPUT`，改用 `data` 回传一个 Uri（图库类应用常见） | 读那个 Uri |
| 3 | 老式写法：回传缩略图 `Bitmap` 在 `extras["data"]` 里 | 自己压成 JPEG 落盘再用 |

你描述的现象是"点拍照之后跳出来一个**选图**界面"——说明那台机器上响应
`ACTION_IMAGE_CAPTURE` 的不是相机，而是某个图库 / 文件选择器。
这类应用正是最容易走第 2、3 条路的，现在都能接住了。

### 4. 接不住的时候**明说**，并给一条能走通的路

三条路都没拿到东西时，弹一个对话框：

> **相机没有返回照片**
> （说明 + 建议）
> **[ 改用「选图」 ]   [ 知道了 ]**

「改用「选图」」直接调起照片选择器。这是照 1.4.1/1.4.2 立下的规矩做的——
**与其让用户对着错误框发呆，不如把能走通的那条路摆在按钮上**。

### 5. 待回填的拍照文件进 `savedInstanceState`

```kotlin
outState.putString(KEY_CAPTURE, pendingCaptureFile?.absolutePath)   // 存
pendingCaptureFile = state.getString(KEY_CAPTURE)?.let(::File)      // 接回来
```

## 四、怎么验证

```bash
python verify_source_pipeline.py    # 64 项，本轮从 51 扩到 64
# 另外 9 个回归脚本
```

新增的 13 项都盯「**改了也不会崩、只是不工作**」这类特征：

| 检查 | 防的是什么 |
| --- | --- |
| 走的是能拿回传 Intent 的契约，且代码里不再有 `TakePicture` | 有人图省事换回 `TakePicture` → 权限又没了 |
| 启动前 `grantUriPermission` 把读写权限授出去 | 授权环节被删 → 又变成 0 字节 |
| 按包名遍历所有能响应拍照的 App | ROM 转发时丢 flag |
| intent 自己也带 grant flag | 双保险被摘掉 |
| 明确写了 `EXTRA_OUTPUT` | 输出位置丢了 |
| 没拿到图时会弹提示 | 又变回静默 |
| 提示框的按钮真接到 `showSourceChooser()` 上 | 按钮摆着不干活 |
| 提示用弹框而不是 `Toast` | 一闪就没，用户正盯着空预览区，会错过 |
| 三条回退路都在（文件 / 回传 Uri / 缩略图 Bitmap） | 图库类应用接不住 |
| 缩略图走类型化 `getParcelable` | 无类型 `get` 在 API 33 已废弃，会破掉「0 警告」 |
| 用户取消时不弹东西 | 按返回键也弹框，很烦 |
| 待回填文件进了 `savedInstanceState` | 界面被相机挤掉重建后接不上 |
| 重建时把它接回来 | 同上，另一半 |

**并且做了反向验证**：把关键判断分别对着"修好后的代码"和"退回 1.4.4 的代码"各跑一遍，
确认它们**只在修好后成立**、退回旧写法一律 FAIL。
（第一遍验证时反而暴露出我自己的降级模拟不完整——没有把整个回退函数删掉，
所以那条检查"看着过了"。补全模拟之后才是真的验证通过。）

> 顺带修掉一个工具自身的隐患：`verify_source_pipeline.py` 原来把工作区路径**写死**成绝对路径，
> 工作区一改名就废。改成和其他脚本一样从脚本所在目录**逐级向上查找**（找不到才退回老路径）。

> **另外一个"自己抓到自己"的小插曲值得记一笔**：第一轮构建出来后，日志里出现了 **2 条 Kotlin 警告**——
> 我用无类型的 `Bundle.get(String)` 取缩略图，而这个 API 在 **API 33 起已废弃**。
> 本工程有「代码级编译警告必须为 0」这条硬规矩，所以：① 改成按版本分支的类型化 `getParcelable(key, Class)`
> （低版本分支保留并加 `@Suppress` 注明原因，因为 minSdk 是 26）；② 顺势把这条也写成检查
> （断言不许出现 `extras?.get(`）。**重新构建后警告回到 0 条。**
> 这也说明一件事：**检查脚本挡不住的东西，构建日志会挡——两边都得看。**

## 七、附：交付时顺手做的一次"多出来的 670 KB"取证

出包的时候发现一件不对的事：**debug 包 7,159,030 B**，而 1.4.2 / 1.4.3 / 1.4.4 的 debug 包一直稳定在 6,478,871 / 6,485,950 / 6,485,954 B。
一版之间**凭空多了 670 KB**，但这版只加了几段拍照代码。既然数字不对，就不能"看着能装就过"。

### 查到的东西

先用自写的 `PK\x03\x04` 扫描，得出"条目间空隙 0 个"；换个脚本再扫，又变成"28 个空隙"。
**两次结论互相矛盾 → 说明扫描方法本身不可靠**（压缩数据里本来就可能出现 `PK\x03\x04` 字节序列，会被当成条目）。
于是改用 `zipfile` 读**中央目录**（这才是权威），重算：

| 指标 | 1.4.4 | 1.4.5（重打前） |
| --- | --- | --- |
| 文件大小 | 6,485,954 B | 7,159,030 B |
| 条目数 | 925 | 925（**名称集合逐一相同**） |
| 条目压缩数据合计 | 6,322,497 B | 6,325,295 B（**只差 2,798 B**） |
| 条目间空隙 | **0 处 / 0 B** | **28 处 / 670,279 B** |
| 全部条目 CRC 校验 | 通过 | 通过 |

把 670,279 B 的空洞当二进制解出来，结构很干净：**30 字节桩头（version / flags / method / CRC / 压缩前后大小 / 文件名长度全是 0）+ 紧跟 `空洞大小-30` 字节的全零 extra 字段**。
这种记录**不是一个合法 ZIP 条目**（合法条目 version 至少是 10 或 20），**不进中央目录、不携带任何数据**，任何 ZIP 读取器都看不见它。

**结论：这 670 KB 是上一次增量打包留下的填充占位，不是内容翻倍、也不是代码膨胀。**

### 怎么证实的

把 debug 产物目录挪走，只重跑 `:app:assembleDebug`：

```
36 actionable tasks: 1 executed, 35 up-to-date
> Task :app:packageDebug        ← 只重执行了打包这一步
BUILD SUCCESSFUL in 41s
```

结果：

| 指标 | 重打后 |
| --- | --- |
| 文件大小 | **6,488,754 B**（少了 670,276 B） |
| 条目间空隙 | **0 处** |
| CRC 校验 | 925 条全通过 |
| 签名 / 对齐 | v2 签名通过、`zipalign -c 4` 通过 |
| 版本 | versionCode 13 / versionName 1.4.5 |
| 权限 | 仍是 `WRITE/READ_EXTERNAL_STORAGE` 且都 `maxSdkVersion=28`（零权限设计没破） |
| 代码级编译警告 | **0 条** |

减少量 670,276 B ≈ 空洞 670,279 B（3 字节差值来自条目微小的尺寸变化），严丝合缝。
**同时 release 包的哈希前后完全一致**（`30d2e210…` 未变）——说明这次重打**只碰了 debug 包，release 包连一个字节都没动**，
你手上要装的这个包和文档里记录的始终是同一个文件。也正因为如此，**这一版不需要升版本号**。

### 顺手修正的一处文档笔误（附一次我自己的误判）

README 的「产物哈希」表写着「SHA-256（前 32 位）」，核对时发现 1.4.4 release 那一串**只有 31 位**
（`e0afe2c5ee209e4566cab833fba3ae4`），结尾少了一个 `c`。

**这里我先走错了一步，值得记下来**：看到 32 位十六进制，我第一反应是"32 位不可能是 SHA-256，
那只能是 MD5"，于是按 MD5 重算、连表头一起改成了 MD5——**这个推断是错的**。
`sha256sum` 之后逐字符比对，才发现**那几串本来就是 SHA-256 的前 32 个字符，四个值全部一一命中**，
表头的写法从头到尾没有问题（"前 32 位"是截断，截断本身完全合法）。
**误判的代价是我一度把一张本来正确的表改成了错的**，发现后立刻改回。

最终结果：表头保持 **SHA-256（前 32 位）**、把缺失的那个字符补上，并把 1.4.5 的两个包补进「本期」表：

| 文件 | 大小 | SHA-256（前 32 位） |
| --- | --- | --- |
| `ASCII图片转换器-1.4.5.apk` | 1,665,512 B | `30d2e2102688bb7f5a5d429d74b7ea91` |
| `app-debug.apk` | 6,488,754 B | `f3627a237a3d838cce00ac9c481f49e8` |
| `old/ASCII图片转换器-1.4.4.apk` | 1,664,100 B | `e0afe2c5ee209e4566cab833fba3ae4c` |
| `old/app-debug-1.4.4.apk` | 6,485,954 B | `5c164e1cabac968caa872ab480f82189` |

> 两条教训：
> 1. **"看着能装"和"数字对得上"是两件事。** 若当时只做签名/对齐核对（那两项本来也都是通过的），
>    这 670 KB 就会跟着包一起交出去；而 debug 包正是将来抓崩溃日志用的那个，
>    多出来的体积反倒容易让人先怀疑到自己头上。
> 2. **不要凭长度去反推摘要算法。** 32 位十六进制**既可能是 MD5，也可能是某个 64 位摘要的前 32 位**，
>    只能实算比对，不能靠推理——这一条我当场踩了。
