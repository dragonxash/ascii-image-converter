# 更新说明 — 1.4.0

**版本**：1.4.0（versionCode 8）
**上一版**：1.3.0（versionCode 7）
**主题**：修掉**文字结果闪退**（两个独立原因）+ 字符宽度上限提到 **1024**、数字可直接输入 + 新增 **PC-98 画风**（自动/手选 16 色 + 网点抖动重现渐变）

## 一、先说闪退：是什么原因，怎么保证不再犯

「一转换就闪退」是**一个崩溃、两个独立原因**。两个都修了。

### 原因 1（主因）：格式化占位符和实参对不上

底部弹出「文字结果」面板时会调这一行：

```kotlin
getString(R.string.text_format_stats, AnsiText.distinctColorCount(text), size)
```

而资源里当初是这么定义的：

```xml
<string name="text_format_stats">%1$s · 用了 %2$d 色 · 约 %3$s</string>
```

**占位符是 `%1$s`（要字符串），传进去的第 1 个实参是 `Int`。**

`Resources.getString(id, args)` 内部就是 `String.format(getString(id), args)`，
类型对不上就在**运行时**抛异常。这条路径一点就炸，所以是「必崩」。

| 分支 | 当时的实际结果 |
| --- | --- |
| 彩色格式（16 色 / 真彩） | `IllegalFormatConversionException: d != java.lang.String` |
| 纯字符格式 | `MissingFormatArgumentException: Format specifier '%2$s'` |

这两种异常**编译期不报、`lintVitalRelease` 也不拦**（`StringFormatMatches` 只是 warning），
只在用户点开那个界面时才炸——这正是它一路活到 1.3.0 的原因。

修正后的定义（中英各一份）：

```xml
<!-- zh -->
<string name="text_format_stats">用了 %1$d 色 · 约 %2$s</string>
<string name="text_format_stats_plain">无颜色 · 约 %1$s</string>
<!-- en -->
<string name="text_format_stats">%1$d colors · %2$s</string>
<string name="text_format_stats_plain">no color · %1$s</string>
```

### 为了不再犯：加了个静态检查脚本

光改定义不够——同样的坑下次换个字符串还会踩。所以加了 `verify_string_formats.py`，检查四件事：

| 检查项 | 拦的是什么 |
| --- | --- |
| 每个 `getString(R.string.X, ...)` 的实参个数 == X 里最大的占位符下标 | `MissingFormatArgumentException` |
| `%d` 位置收到疑似 `String` 的实参 | `IllegalFormatConversionException` |
| 串里有裸 `%`（如 `"50% off"`）却带了实参 | `UnknownFormatConversionException` |
| 中文 / 英文两份资源的占位符集合必须一致 | 切语言才崩的那种 |
| **（新增）间接引用点名** | `getString(someResId, ...)` 这类第一个实参不是 `R.string.字面量` 的调用 |

最后一条是这轮补上的：原来的正则只认 `R.string.X` 字面量，
于是 `getString(hintRes, min, max)` 这种**间接传 id** 的写法整个是盲区，查都不查。
现在这类调用会被逐条点名列出来（当前 6 条，都是枚举的 `titleRes` / `labelRes`，人工过目即可），
顺手把工具函数签名从「传资源 id」改成「传拼好的文本」，从写法上消掉这个坑。

> 这个脚本是**回归验证过的**：把 bug 改回去，它确实报 2 条未通过。

### 原因 2（顺手一起修的）：预览着色会撑爆内存

修完上面那个之后，「文字结果」面板还有第二个雷，而且在你要的 1024 宽度下**必炸**。

预览要把 ANSI 文本转成彩色显示，做法是给每一段同色字符加一个 `ForegroundColorSpan`：

| 格式 | 每行的 span 数 | 1024 列 × 上千行时 |
| --- | --- | --- |
| 16 色 / PC-98 | 每行最多 16 段（同色自动合并） | 几万个，没事 |
| **真彩（24 位）** | **每段 1 个字符** → span 数 = 字符数 | **上百万个 span → OOM** |

现在预览最多着色 **20 万字符**，超了就在信息行显示
「预览已截断，复制/保存的是完整文本」。

**只有预览被截**——复制、保存文件、分享拿到的都是**完整文本**，一个字不少。

## 二、字符宽度上限：256 → 1024

| 项目 | 1.3.0 | 1.4.0 |
| --- | --- | --- |
| 字符宽度上限 | 256 列 | **1024 列** |
| 网格格子总数上限 | 无 | **1,500,000**（新增） |

放宽上限就必须同时加个总格子数的闸——列数是你说了算的，
行数是按长宽比算出来的，一张竖图 1024 列就能到上千行。
格子总数封顶后，超了会把**行数**砍下来（极端长宽比的图会被略微压扁，好过直接 OOM）。

## 三、数字可以直接输入

「字符宽度」和「原图彩色填充」这两个数字，现在**点一下就能敲**。

拖滑杆要精确停在某个值上很难，比如想试 512 列，滑杆上根本对不准。
输入范围外的值（宽度 16~1024、填充 0~100）会提示一句、**不动**当前值——
边删边打的过程中必然是空字符串，不能因为一个中间态就把调好的参数清掉。

## 四、PC-98 画风：你要的「渐变用 16 色组合出来」

这是这版的主要功能。两条路都通：

| 方式 | 怎么用 |
| --- | --- |
| **整档预设** | 设置面板最上面的预设标签多了一个 **PC-98**，点一下全给你配好（320 列 + 色块 + 16 色 + 网点抖动） |
| **手动开关** | 设置面板里的 **PC-98 画风** 开关，配合下面的「中间色处理」和「调色板」，可以只对画面套 16 色、字符照旧 |
| **自动选色** | 默认。从画面里用**中位切分**挑 16 个最有代表性的颜色（每张图挑出来的都不一样） |
| **手动选色** | 点「调色板」→ 4 套现成的（PC-98 标准 16 色 / 怀旧暖色 / 冷调夜色 / 16 级灰阶）任选，或点任一色块用三根滑杆逐通道调（每通道 0~15 级，对应 12 位精度），也能一键回「自动取色」 |

### 关键：中间色怎么"用 16 种颜色组合出来"

16 色能直接画出来的只有 16 种，像渐变这样的中间色按理画不出来。
办法是**抖动（dithering）**——相邻格子轮流用两种颜色，隔远看合成成中间色，
就是老杂志印刷网点那套把戏。三档可选：

| 档位 | 做法 | 观感 |
| --- | --- | --- |
| **不抖动** | 每格直接取最接近的颜色 | 色块感最强，会出现明显色阶断层 |
| **网点抖动**（默认） | Bayer 8×8 网点矩阵 | 颗粒规则、稳定，最像当年的印刷网点 |
| **误差扩散** | Floyd–Steinberg，把误差摊给邻居 | 渐变最平滑，代价是多了点噪 |

**抖动幅度不是写死的魔数**，是按「调色板里相邻两色的平均距离」算的——
换任何一套 16 色都能自适应（黑白 2 色的间距 127.5，标准 16 色是 42.5，挤在一起的灰只有 8.5）。

### 效果实测（`verify_pc98_dither.py`，22 项全过）

拿一条横向渐变跑三档，量「隔远看」的误差（8×8 块平均色差，越小越接近原图）：

| 模式 | 逐格色差 | 8×8 块平均误差 |
| --- | --- | --- |
| 不抖动 | 31.20 | 27.34 |
| 网点抖动 | 32.71 | **18.26** |
| 误差扩散 | 37.91 | **5.02** |

误差扩散把「隔远看」的误差压到了不抖动的 **1/5.4**。

**注意看最左边那列——它是变大的，这不是 bug。**
抖动的本质就是：为了让**局部平均**对，单个格子必须故意选一个「不那么准」的颜色，
两种颜色交替出现，眼睛才会把它看成中间色。
所以拿逐格误差评价抖动是错的指标；这一条我写进验证脚本里当断言了，
顺便留了句提醒：**要是哪天有人「优化」到逐格误差变小了，多半是把抖动改成了不抖动。**

最能说明问题的是这个例子：纯灰 `#888888` + **只有黑白两色**的调色板。

| 模式 | 结果 | 平均亮度 |
| --- | --- | --- |
| 不抖动 | 整片被压成**纯白** | 255（原灰 136，差 119） |
| 网点抖动 | 被拼成**黑白相间**的网点 | 143（差 **7**） |

—— 这就是你说的「用 16 种颜色组合来显示渐变色」，在同一片平涂区域里就看得见。

### 相关说明

- **heatmap 伪彩色功能没动**，还在（那是「文字导入」时按亮度走光谱的那套）。
- 「PC-98 画风」和「只保留色块」是**两个独立开关**：前者只管配色，后者只管画像素块还是画字符。
  预设 PC-98 把两个都打开了（色块 + 16 色＝复古像素画），但你也可以只开其中一个。
- 16 色模式没开时，「中间色处理」和「调色板」会**置灰**——不置灰的话用户点了没反应更懵。

### ⚠️ 需要你实机确认的事

**这一版的改动全部只做了编译验证、包内核对和算法级验证，没有在真机/模拟器上跑过。**

已经能从包里确认的（所以这几条风险较低）：

- versionCode / versionName / 包名 / 启动 Activity 都对
- 修好的那两条字符串，从 release 包的资源表里反解出来**实际值就是修好的版本**，中英各一份
- 新增的 `Pc98Quantizer`、`DitherMode` 两个类，以及 22 个新增方法，在 `mapping.txt` 里**全都存活**（没被 R8 裁掉）

还没法在代码层面验证的：

1. **UI 交互一次都没点过。** 三个新面板（PC-98 开关 / 中间色处理标签 / 调色板面板）和两个数字直输对话框，
   逻辑是走查确认的，布局效果只有上机才知道。
2. **闪退的根本原因是推出来的，不是复现出来的。** 占位符类型不匹配这个结论，
   依据是 `Resources.getString(id, args)` 内部就是 `String.format`，加上
   参数类型逐一对过；并用一个 Java 小程序把两种异常（`IllegalFormatConversionException` /
   `MissingFormatArgumentException`）都复现到了。但**原始崩溃没在这台机器上复现过**。
   所以如果装上还崩，请照 `排错说明-如何取错误详情.md` 抓一份 logcat 给我——
   那边有完整异常栈，一看就知道是哪个环节。
   **要看崩溃日志请装 `app-debug.apk`**，它的取证信息更完整。
3. **调色板面板是叠在设置面板上的第二个底部弹窗**，这种叠法在小屏上可能显得挤，实机看了不对我再改。
4. **1024 列在大图上会很慢。** 格子总数封顶 150 万，但 150 万格的转换本身就要几秒，
   加上真彩文本编码，低端机可能卡一下。这是我预判的风险点，但没实测过。
