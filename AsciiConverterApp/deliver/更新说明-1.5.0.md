## 一、加一门语言要动**四处**，漏一处都是静默失效

这次最值得记下来的不是"翻译了多少条"，而是**这门语言的开关散在四个地方**，
而且**四处漏掉任何一个都不会报错**——不崩、不提示、编译也过，
只是"选了没反应"或者"部分界面还是旧语言"：

| 位置 | 作用 | 漏掉会怎样 |
| --- | --- | --- |
| `core/AppLanguage.kt` 的枚举 + `selectable` | 语言菜单的项目来源 | 菜单里**根本没有这一项** |
| `res/values-ja/strings.xml` | 日文文案 | **静默回退成中文**（缺键不算错），出现中英日混杂 |
| `res/xml/locales_config.xml` | Android 13+ 的系统 per-app language | 系统设置 → 应用 → 语言 里**看不到日语** |
| `app/build.gradle.kts` 的 `localeFilters` | 告诉 aapt 只保留哪些语言的资源 | **资源被直接裁掉** → 装机后"选日语没反应、界面还是中文"，而本地编译毫无异常 |

最后一条是这次最需要警惕的：`localeFilters` 是 1.4.0 为了压体积加的
（原来只留中英），它是个**白名单**。加了 `values-ja/` 却没加进白名单，
aapt 会把日文资源当垃圾一起裁掉——**编译器一个字都不会说**。

### 1. `AppLanguage.kt`

```kotlin
System("", R.string.lang_system),
Chinese("zh", R.string.lang_chinese),
English("en", R.string.lang_english),
Japanese("ja", R.string.lang_japanese);     // ← 新增

val selectable = listOf(Chinese, English, Japanese, System)   // ← 菜单顺序也在这儿
```

语言弹窗是**由 `selectable` 动态生成**的（`MainActivity.showLanguageDialog()`），
所以菜单那边不用改代码，加枚举项 + 放进 `selectable` 就够了。

### 2. `res/values-ja/strings.xml`

按现有 `values/`（中文，162 条）逐条译。**键必须一个不多一个不少**，
因为它在下面第 2 节说的"静默回退"。

日语用词上跟了 Android 官方日文界面的习惯：`画像` / `文字` / `撮影` / `保存` / `共有` /
`設定` / `表示言語` / `カメラ` / `ギャラリー`，提示语统一用 `〜してください`、
错误统一用 `〜に失敗しました：`，全角冒号。

### 3. `res/xml/locales_config.xml`

```xml
<locale android:name="zh" />
<locale android:name="en" />
<locale android:name="ja" />   <!-- ← 新增 -->
```

### 4. `app/build.gradle.kts`

```kotlin
localeFilters += listOf("zh", "en", "ja")   // ← 新增 ja
```

> 顺带说明一个容易误会的地方：`localeFilters` 里写着 `zh`，但资源目录里**没有 `values-zh/`**。
> 这是有意的——**默认资源 `values/` 本身就是中文**，`zh` 会落到默认资源上，所以不用单开目录。
> aapt2 报的语言列表是 `locales: '--_--' 'en' 'ja'`，其中 `--_--` 就是那份中文默认资源。

## 二、翻译时真正会踩的坑

### 1. 格式占位符必须原样保留

`%1$s` / `%2$d` 这类东西**少一个就会在运行时直接闪退**
（`String.format` 参数对不上，抛 `IllegalFormatException`），
而且**编译期完全查不出来**——它在资源里就是一段普通文本。

这次把 162 条全部逐条比对了占位符的**序号、类型、出现次数**，
日文版与中文基准**零偏差**（`verify_locales.py` 会一直盯着这件事）。

### 2. 字面量 `%` 必须写成 `%%`

`settings_color_fill_value` 是 `%1$d%%`——那个"100%"的百分号不转义，
Android 会把它当格式符解析。日文版照写 `%1$d%%`。

### 3. 换行是 `\n`，不是真的回车

`import_desc`、`capture_empty_message`、`about_message` 这几条长文案里有 `\n\n`。

### 4. 缺键不会报错

这是 Android 资源系统的设计：某个语言缺了键，就**静默回退到默认资源**
（本 App 默认是中文）。所以"漏译一条"的后果不是崩溃，而是
**日文界面里混着一条中文**——只有真的把界面切到日语才会看见。

正因为这样，这次没有靠人眼，而是写了脚本钉住（见下）。

## 三、新增校验脚本 `verify_locales.py`

按家规「**新增一类风险就补一个校验脚本**」——"漏一门语言的某一处"这次是新风险，
所以补了 `verify_locales.py`。

**它检查 20 项：**

| 组 | 检查内容 |
| --- | --- |
| 四处对齐 | 枚举 ↔ `res/values-*` 目录 ↔ `locales_config` ↔ `localeFilters` 是否**两两一致**；`selectable` 是否覆盖全部语言且项名合法 |
| 键集 | 各语言的键集与中文基准**完全一致**（缺 / 多都报） |
| 占位符 | 各语言的占位符**种类、数量、出现顺序**与基准一致 |
| 转义 | 没有裸 `%` |
| 空值 | 没有空白条目（翻译漏成空串也算） |
| 菜单文案 | 语言菜单用的 `lang_*` 在每个语言里都存在 |

**反向验证（这一步不能省）**：新加的检查必须"把代码改回坏写法喂进去，确认它会 FAIL"，
否则形同虚设。这次三种坏法都试了：

| 改坏方式 | 结果 |
| --- | --- |
| 从 `values-ja` 删掉 `lang_japanese`（模拟漏译） | **FAIL** 18/20，点名「字符串条目数齐全」+「语言菜单的标签文案齐全」 |
| 把 `settings_char_width_value` 的 `%1$d` 改成 `%1$s` | **FAIL** 19/20，点名「格式占位符种类与基准一致」 |
| `localeFilters` 退回 `listOf("zh", "en")` | **FAIL** 19/20，点名「localeFilters 与枚举一致」 |

还原后回到 20/20。**三种坏法都能被检出**，这条校验才算真有作用。

顺带把两个老脚本里**硬编码的 `zh/en` 双语言循环**扩展成了三语言：
`verify_preview_zoom.py` 第 10 节、`verify_source_pipeline.py` 的语言检查段，
否则日文资源根本不在它们的视野里。

**校验脚本数量因此从 根目录 10 / `deliver/` 9 变成 根目录 11 / `deliver/` 10。**
`02-check.sh` 与 `00-先看我-迁移说明.md` 里的期望值也同步改了。

## 四、怎么验证

```bash
cd workspace

# 1. 编译（release + debug）
./build-app.sh assembleRelease assembleDebug
#    → BUILD SUCCESSFUL in 1m 50s

# 2. 代码级警告必须为 0
grep -c "^w: file://" <构建日志>          # → 0

# 3. 全套校验脚本（两边都要真跑）
for f in verify_*.py; do python "$f" >/dev/null 2>&1 && echo "PASS $f" || echo "FAIL $f"; done
#    根目录 11/11 PASS
cd AsciiConverterApp/deliver
for f in verify_*.py; do python "$f" >/dev/null 2>&1 && echo "PASS $f" || echo "FAIL $f"; done
#    deliver/ 10/10 PASS
```

**另外单独确认了「日文真的进了包」**——光看编译过不算数，
因为 `localeFilters` 那个坑正是"编译通过、资源没了"：

```bash
aapt2 dump badging ASCII图片转换器-1.5.0.apk | grep locales
#   → locales: '--_--' 'en' 'ja'          （--_-- 就是中文默认资源）

aapt2 dump resources ASCII图片转换器-1.5.0.apk | grep -A3 "string/app_name"
#   → resource 0x7f100022 string/app_name
#       ()   "ASCII 图片转换器"
#       (ja) "ASCII 画像コンバーター"
#       (en) "ASCII Image Converter"
```

再从字节层面复核了一次 `resources.arsc`：`ASCII 画像コンバーター`、`画像を選ぶ`、
`システムに従う`、`日本語`、`変換中…` 等抽样字符串都实际存在（UTF-8 编码）。

**签名**：`apksigner verify --print-certs` → v2 方案通过、RSA 2048、证书 SHA-256 仍是 `37c4513…`。

## 五、1.5.0 与 1.4.5 的包内差异（逐条目比对过）

两个包条目数都是 **781**，一个不多一个不少；**58 个条目内容有变化**，
差异范围与"只动了资源系统"完全吻合：

| 差异项 | 说明 |
| --- | --- |
| `resources.arsc` | 530,280 → 543,764 B，多出来的就是日文那 162 条 |
| `res/*.xml`（**53 个**） | 编译后的布局/资源，多数**尺寸不变但 CRC 变了**——因为新增字符串让资源 ID 重排，引用了这些 ID 的布局得重编 |
| `classes.dex` | 1,520,412 → 1,520,460 B（+48 B），`R.string.lang_japanese` 让 R 类多一个字段 |
| `AndroidManifest.xml` | 7,528 → 7,528 B（同尺寸但内容变，versionCode / versionName） |
| `assets/dexopt/baseline.prof` | +2 B |

**算法没动**：`verify_release_chartable.py` 是从**发布包自己的 `classes.dex` 里**
把 92 级字符表取出来比对的，1.5.0 通过 → 交付包里那份字符表与参考实现仍然逐字节一致。

## 七、还是**没有真机测试**

构建环境里**依旧没有可用的安卓设备或模拟器**，所以：

- **日文界面一次都没在真机上看过。** 我能保证的是：资源齐、键集一致、占位符一致、
  `ja` 确实在包里、四处配置对齐。**但"排版会不会挤、长文案会不会换行难看"
  这类只能上手看的，一条都没验过。**
- 特别建议上手时看一眼这几处**日文比中文长**的地方：
  `settings_blocks_only_desc`、`capture_empty_message`、`batch_all_failed_message`、
  `about_message`——日文文案普遍比中文长 20~40%，小屏上容易挤。
- 语言切换本身（选日语 → 界面重建 → 是否真的变日文）**依赖 androidx 的
  per-app language + 自写的 `wrap()` 兜底**，这条链路的真机行为**一直是未验证状态**
  （1.1.1 修「选了中文还是英文」时就写在文档里了）。这次改日文等于又给这条链路
  加了一个待验证的语言。

装机后麻烦重点试：**右上角菜单 → 语言 → 日本語**，看是否立刻切成日文；
再切回简体中文；再切「跟随系统」。有任何一条不对，把现象说出来我改。
